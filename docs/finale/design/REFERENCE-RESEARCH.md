Logged-in Linear application screens were not accessible; its public feature overview was read and an image link failed. This is a reference study, not a user study or product certification.

## Actual visual exploration

Three original HTML interface explorations were rendered and visually inspected. They were explicitly labelled layout studies with no live telemetry. Source and screenshots are preserved privately under project work/finale/ultimate-experience/directions.

| Direction | Composition | Assessment |
|---|---|---|
| Precision / Cyan | Central optical viewport, compact evidence rail, graphite/navy surfaces, cyan navigation/action accent | Selected. Clear hierarchy, efficient desktop observation/action grouping, differentiated warning colors; naturally adapts to stacked trainee controls |
| Analytical / Amber | Broad optical area with lower split evidence panels, warm charcoal surfaces and small radii | Readable but longer vertical travel between contact selection and observation. Amber as primary competes with caution states |
| Field / Sage | Left evidence rail, right viewport, green/teal surfaces and softer rounded controls | Calm but less distinctive from RC2; left evidence rail competes with persistent app navigation |

Selection is a documented design judgement, not a measured superiority score. The integrated app must still pass functional, keyboard, contrast, responsive and performance checks. Its simulation view renders only real observed contacts; there are no decorative detections. Prototype placeholders never become production telemetry.

## Route baseline

All13 routes were inspected in actual Chrome using the RC2 production assets before rebuilding: training, Crew, RapidID, Unit, Instructor, Analytics, Exercises, Recorded, Transfer, Compliance, Evidence, Evaluation and Benchmark. Authentication was also captured. The copied synthetic QA database supplies real persisted sample records; no production learner data is used. The first AAR URL was incomplete and showed unavailable review; a loaded full-ID AAR is required during functional validation.

Confirmed weaknesses: legacy default; profile/settings push the viewport far below primary action; analytics expands every detail at once; compliance leads with93engineering findings; small inconsistent panel text; plain resource panels; repetitive contextual caveats. Existing RC2 clipping/contrast fixes are preserved. Changes address information order, discovery and trustworthy workflow states, not merely accent color.

## 14 October structural course correction

The user rejected the original8048 palette studies. They remain historical explorations and are not the selected final product direction. Three new functional architectures were built and operated in the Codex in-app browser. Each has actual preparation, active, selected-contact, officer, review and390px captures under the private project `work/finale/ultimate-experience/structural-directions/screenshots` directory. They are explicitly synthetic layout studies, not VYUHA validation runs.

| Architecture | Structure and working interaction | Useful product principle | Tradeoff |
|---|---|---|---|
| A Spatial Mission Command | Dominant real local Three.js environment; horizontal navigation; selected evidence inspector and common decision dock; actual local designation/classification/response records | Keep simulation central and evidence adjacent to decisions | Prototype officer/review surfaces are too sparse; requires richer actual persisted evidence |
| B Sensor Intelligence Laboratory | Horizontal document navigation; linked radar/optical/RF instruments; shared ledger; prerequisite and observation-loss guards | Coordinate selected-contact evidence and disclose reference truth separately | Three equal channels compete with the3D viewport; synthetic RF spectra cannot be imported as measured product data |
| C Mission Simulation Theatre | Mission chapters; illustrated preparation environment; progressive contact inspector; local intervention lifecycle; investigative review | Compose preparation and completion around a coherent task, with deliberate typography and focus handoff | Illustration is not3D simulation; scene contacts are scripted fixtures; prose must stay compact under training pressure |

**Selected hybrid:** A supplies the active spatial workstation and one decision surface; C supplies composed preparation/completion and reduced permanent navigation; B supplies linked evidence organization for the actual RF/IFF/Fusion selectors. Preserve real local services, measured/synthetic distinctions, visibility filters and authoritative review. No prototype sensor trace, uncertainty radius, score or static trainee row becomes production evidence.

The root browser completed A's designate→hypothesis→hold sequence and C's designation→declaration→hold→review plus local queued/applied intervention. B correctly rejected classification with Unknown identity, then accepted an explicit hypothesis and Hold. Each390px page had no outer overflow. These tests establish prototype interactions only. Production integration needs new all-route, responsive, accessibility, performance and release verification.

### Additional resource study actually performed

The official [Anthropic frontend design guidance](https://raw.githubusercontent.com/anthropics/skills/main/skills/frontend-design/SKILL.md) informed subject-specific composition, restrained motion, deliberate type and rejection of identical card kits. It was studied as external guidance; no package or agent configuration was installed. The three architectures spend visual emphasis on the observation environment and decision context rather than ornamental telemetry.

[21st MCP](https://github.com/21st-dev/magic-mcp) is now a compatibility proxy for a hosted authenticated service; no callable21st tool is configured here, no key requested and no runtime dependency added. [shadcn/ui](https://ui.shadcn.com/docs), [Radix](https://www.radix-ui.com/primitives), [Magic UI](https://github.com/magicuidesign/magicui), [Motion Primitives](https://github.com/ibelick/motion-primitives), [Motion](https://motion.dev/docs/react) and [Lucide](https://lucide.dev/guide/) were reviewed through primary documentation/repositories. Existing native controls, lightweight focus management and installed Lucide remain the integration choice; no broad framework migration or animation dependency was introduced. Component-specific license/cost review remains necessary before copying third-party implementation.

[Playwright MCP](https://github.com/microsoft/playwright-mcp), [Chrome DevTools MCP](https://github.com/ChromeDevTools/chrome-devtools-mcp) and [Context7](https://github.com/upstash/context7) were examined as tooling options. They are not callable installed tools in this session. Existing CUA browser controls provided actual DOM interaction, screenshot capture, viewport settings and console access. Do not claim DevTools traces or theseMCP integrations were executed.

Plugin discovery returned Figma and MagicPath as available but uninstalled/unconnected, with prior suggestions already recorded. Neither was invoked as a design tool. Their absence did not block local implementation; the browser, code-native studies, source tools and independent agents were actually used.
